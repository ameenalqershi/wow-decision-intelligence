# Join development

Ask the repository owner for named collaborator access. Read the [roadmap](planning/roadmap.md), [architecture](docs/design/architecture.md) and [engine semantics](docs/design/engine.md). Use .NET 10 SDK, Git, GitHub CLI, jq and Node for the scope checker. Production language is C#; Node is limited here to development tooling. Keep solver binaries, credentials and real customer data out of commits.

1. Select an open unassigned issue whose listed prerequisites are closed. Several people may share a GitHub login in a controlled development workspace. Each session must have a unique local worktree and an issue claim. The issue coordinator may split work with explicit boundaries.
2. From a clean checkout of this repository, run `bash tools/claim.sh ISSUE short-handle` in Bash (Git Bash on Windows). The remote tag is a create-once reservation. Only the creator of the successful reservation starts work. Records survive session loss. The command prints the worktree and branch. If metadata synchronization fails after reservation, the tag still owns the claim; follow the recovery instructions below.
3. Comment on the issue with owned paths, expected contract changes and intended verification. For a shared contract, open a small contract PR before dependent implementations. Coordinate overlapping file or schema changes. Feature branches never overwrite another developer's changes.
4. Run affected checks, open a PR linked to the issue, and give other contributors a stable contract revision. Rebase only your own branch or merge the latest main; do not rewrite main. A merge conflict still requires review. Inspect dependent issues for assumptions invalidated by the change.
5. Close the issue with evidence after the PR is merged or the documented research deliverable is accepted. Remove the active label. Retire the reservation on closure or handoff after confirming ownership. Retain the branch until safely merged.

**Claim recovery.** Inspect the annotated tag with `git fetch origin tag work-claims/ISSUE` and `git show work-claims/ISSUE`. Contact the recorded owner before takeover. If creation succeeded but issue metadata failed, assign the existing owner and mark status:active on the issue; create a worktree from origin/main if missing. To release, inspect the remote tag object ID and use an exact lease: `git push --force-with-lease=refs/tags/work-claims/ISSUE:EXPECTED_TAG_OBJECT origin :refs/tags/work-claims/ISSUE`. Delete only your matching local reservation afterwards. The lease prevents deleting a newer claim. A contributor with no push permission can use a fork and ask a maintainer to reserve their issue.

**Contract ownership.** Model team owns EDG/UDIR/schema, runtime team owns solver capabilities, verification team owns original-model checks, integration team owns external mappings and UI team owns presentation. Until named maintainers accept these roles the repository owner reviews cross-cutting changes. Do not register fictional reviewers. Record behavioral changes in the relevant design and issue together.

**Definition of done.** Match acceptance criteria, attach commands/results and negative cases, identify data migrations and evidence strength, check dependency impacts, and document OSes actually tested. CI annotations can distinguish account limits from a failed test. If hosted CI cannot start, record that fact and supply local evidence without claiming cross-platform validation.
