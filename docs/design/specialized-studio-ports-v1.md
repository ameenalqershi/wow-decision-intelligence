# Specialized Studio logical application ports · edition 1

Approved design baseline for SP02 review; not a public HTTP route, SDK DTO, storage migration, deployed endpoint or feature completion. The user-directed audit accepts the logical operations, ownership and invariants below. Provider teams must approve and implement concrete versioned payloads, limits and conformance before claiming their features. See the accepted [pilot dictionary](pilot-field-dictionary-v1.md), [UDIR](udir-v1.md), [solver contract](solver-contract.md), [registry](model-registry.md), [connector contract](connector-contract.md), [identity](enterprise-identity.md), [enterprise persistence](enterprise-persistence.md) and [operating modes](operating-modes.md). The eight original ports and 17 pilot field IDs remain unchanged.

## Common contract

Every model/run operation uses trusted tenant + immutable model/revision identity (and run where applicable). Tenant comes from the authorized application context, not a caller-supplied identity override. Local host pins its explicit workspace; enterprise authorizes before lookup; hybrid transfers require explicit approval. All IDs are ordinal nonblank strings. Required values have no inferred default. Optional observed values remain null, not zero. Exact rational values use the canonical UDIR representation when wider than the pilot number profile; never silently round. All associated data is tenant-confidential except published synthetic fixtures. A digest is lowercase SHA-256 of exact bytes, not a permission or independent proof. Errors are scoped, redacted diagnostics; unknown/unavailable is distinct from a successful empty result. Mutations reject stale expected versions and conflicting retries; atomic commit or no change. Cancellation and termination are not mathematical statuses. The provider defines versioned request/response envelopes and stable diagnostic codes before binding the UI.

No new pilot field IDs are introduced. These logical field profiles intentionally defer concrete provider-specific DTO member names, numeric limits, distribution parameters, budget schemas, authorization mutation routes and configuration schema versions to the indicated feature owners. The approved logical contract does not replace the owner's independent mathematical/operational acceptance. A screen may develop its layout and unavailable-capability state against these boundaries; it may not assert a real provider operation until the relevant capability is qualified.
